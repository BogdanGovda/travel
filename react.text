Базова теорія
Сприймайте JSX як синтаксис, що трансформується у створення React-елементів.
Тримайте props незмінними і піднімайте ownership стану на правильний parent-рівень.
Використовуйте стабільні key у списках для збереження ідентичності і уникнення UI-багів.
Оновлюйте стан імутабельно для передбачуваного rerender.
Дробіть UI на когезивні компоненти з явними відповідальностями.
Уникайте логіки, що залежить від неявних припущень про порядок рендеру.
Документуйте контракти компонентів через зрозумілу семантику props.
Не змішуйте side effects з фазою render.


Повна теорія з прикладами коду
Основи React: спочатку контракти
На співбесідах по React найчастіше провалюються не через синтаксис, а через невміння пояснити контракти між UI, станом і async-даними.

Описуйте кожен модуль через явний input, output, ownership і failure-поведінку. Якщо залежність падає, fallback має бути визначений до реалізації.

Сильна інженерна відповідь містить tradeoffs, telemetry-сигнали і rollback-умови, а не лише happy-path.

Скетч модульного контракту
type ScreenContract = {
  input: { routeId: string; query: Record<string, string | undefined> };
  output: { items: Array<{ id: string; title: string }>; canRetry: boolean };
  failure: "network" | "forbidden" | "validation";
};

function mapApiToScreen(payload: unknown): ScreenContract["output"] {
  return { items: [], canRetry: true };
}
Детерміновані переходи стану
Якість стану визначається ясністю переходів: що може статися, що не може, і який fallback.

Коли async-запити змагаються, комітити стан має лише один owner. Усі інші відповіді скасовуються або ігноруються за політикою.

Детермінована state-модель простіша для тестів, моніторингу і безпечніша для еволюції під тиском продукту.

Guard переходів стану
type UiState = "idle" | "loading" | "success" | "error";

function canTransition(from: UiState, to: UiState): boolean {
  const allowed: Record<UiState, UiState[]> = {
    idle: ["loading"],
    loading: ["success", "error"],
    success: ["loading"],
    error: ["loading"],
  };
  return allowed[from].includes(to);
}
Операційний плейбук продуктивності
Робота з продуктивністю починається з відтворюваних доказів: profiler-трейсів, таймінгів взаємодій і шляхів скарг користувачів.

Спершу оптимізуйте дорогі переходи, потім оцінюйте, чи мемоізація або кеш реально знижують latency без регресій коректності.

Кожна performance-зміна має містити вимірюваний before/after і rollback-тригер на випадок деградації.

Простий helper для performance mark
export function measure<T>(name: string, fn: () => T): T {
  const start = performance.now();
  const result = fn();
  const end = performance.now();
  console.info(`[perf] ${name}: ${(end - start).toFixed(2)}ms`);
  return result;
}
Тестування для confidence і швидкості
Якість тестування — це не кількість тестів, а ratio довіри до вартості під постійними змінами.

Використовуйте поведінкові асерції на межах компонентів і контрактні перевірки в integration-точках, де регресії дорогі.

Flaky-тести потрібно швидко triage-ити з ownership, root-cause мітками та детермінованими фіксами.

Схема behavior-орієнтованого тесту
type Case = { name: string; arrange: () => void; act: () => void; assert: () => void };

const caseItem: Case = {
  name: "shows fallback when request fails",
  arrange: () => {},
  act: () => {},
  assert: () => {},
};

Тримайте неймінг і структуру послідовними між feature-модулями.
Рев'юйте модулі через failure-mode, а не лише через happy path.

Якість стану і детермінована поведінка

Використовуйте передбачувані патерни оновлення, щоб спрощувати дебаг і rollback.
Захищайте async-переходи від race condition при швидкій навігації.
Сприймайте інвалідацію кешу як продуктову подію, а не випадкову технічну дію.
Практика

Додайте telemetry-події для timeout, canceled request і ignored stale response.
Опишіть мінімальні reproducible-сценарії для кожного класу критичних state-багів.
Продуктивність через вимірювання, а не фольклор
Починайте оптимізацію з profiler-трейсів і user-visible latency-метрик.
Оптимізуйте критичні interaction-шляхи до мікрооптимізації leaf-компонентів.
Застосовуйте мемоізацію і кеш там, де є вимірювана користь під реальним навантаженням.
Відстежуйте p95/p99 затримки взаємодії для раннього виявлення tail-регресій.
Практика
Зафіксуйте baseline-метрики до і після однієї оптимізаційної гілки.
Опишіть rollback-умову для кожної оптимізації, що несе ризик коректності.
Додайте CI-перевірки performance-бюджетів для критичних екранів.
Тестова стратегія для стабільної доставки
Використовуйте unit-тести для детермінованої доменної поведінки і pure-трансформацій.
Використовуйте integration-тести для меж routing, state і UI-контрактів.
Використовуйте E2E для найцінніших user-journey і критичних бізнес-флоу.
Сприймайте flaky-тести як дефекти архітектури і детермінізму.
Практика
Визначте пропорцію тестової піраміди команди і обґрунтуйте її через ризики.
Створіть flaky-test triage-чекліст з ownership і SLA.
Додайте один contract-тест для кожного критичного API-to-UI мапінгу.
